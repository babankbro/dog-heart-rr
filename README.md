# EKG R-Peak Pipeline

ตรวจหาจุด R peak บนภาพคลื่นไฟฟ้าหัวใจจากกระดาษกราฟ ด้วยโมเดล YOLO สองชั้น
พร้อมตัวช่วยจาก image processing ที่ทำงานต่อได้แม้โมเดลชั้นสองจะไม่ตอบ

```
ภาพเต็ม ──Blackhat──> โมเดลครอป ──> กล่องจังหวะ
                                        │
                    หายอด R จากภาพ (anchor) ─┤
                                        ├──> ครอปตามสัดส่วนชุดเทรน ──ink mask──> โมเดลจุด ──> จุด R
                                        │                                            │
                                        └──────── รวมผล + ตัดจุดซ้ำ + flag ──────────┴──> CSV
```

## เริ่มใช้งาน

```bash
docker compose up -d
```

เปิด <http://localhost:8000> วางภาพไว้ใน `data/` หรืออัปโหลดผ่านหน้าเว็บ แล้วกดตรวจจับ

การติดตั้งบนเซิร์ฟเวอร์จริง (HTTPS + รหัสผ่านหน้าเว็บ) ดู [`deploy/README.md`](deploy/README.md)

สัตว์แต่ละตัวมี **ประเภท** (`group`) ได้ เช่น `Normal` / `B1` ใช้กรองรายชื่อจากแถบด้านซ้าย
ผลที่วิเคราะห์แล้วถูกเขียนลงดิสก์ที่ `out/results/` **กดวิเคราะห์ครั้งเดียวพอ**
เลือกสัตว์ตัวไหนก็เห็นผลทันที และผลไม่หายไปกับการรีสตาร์ต container

ภาพของสัตว์ตัวเดียวกันถูกจัดกลุ่มเข้าหน้าเดียว (`data/<รหัส>/...` + ดัชนี `patients.json`)
สร้างตัวใหม่ อัปโหลดหรือลบภาพได้จากหน้าเว็บ ภาพเก่าที่วางแบน ๆ ใน `data/` กดปุ่มจัดกลุ่ม
ให้ย้ายเข้าโฟลเดอร์ตามรหัสที่อ่านจากชื่อไฟล์ได้ ผลที่วิเคราะห์แล้วถูกจำไว้ฝั่งเซิร์ฟเวอร์
การสลับแท็บหรือเปลี่ยนภาพจึงดึงผลเดิมขึ้นมาเลย ไม่วิเคราะห์ซ้ำ

| แท็บ | ใช้ดูอะไร |
|------|-----------|
| ภาพรวมของสัตว์ | ทุกภาพของตัวนั้นเรียงในหน้าเดียว พร้อม HR และจำนวนจังหวะของแต่ละภาพ |
| ภาพผลลัพธ์ | ภาพเต็มพร้อมกรอบจังหวะและจุด R (แดง = โมเดลยืนยัน, ส้ม = จาก anchor) เลื่อนซูมได้ |
| ครอปที่ป้อนโมเดล | ครอปจริงที่ส่งเข้าโมเดลจุด ใช้เทียบด้วยตากับภาพชุดเทรน |
| binarization + preprocessing | ภาพที่ป้อนโมเดลครอป **ก่อน**ตีกรอบ, ครอปที่ป้อนโมเดลจุด **หลัง**ตีกรอบ, และ ink mask ของจังหวะเดียว — ปรับวิธีและค่าได้ เห็นผลทันที |
| RR interval (mm) | ระยะระหว่างจังหวะเป็นมิลลิเมตร พร้อมกราฟแท่งรายช่วง ค่าเฉลี่ย ส่วนเบี่ยงเบน และจำนวนช่องกริด |
| ตารางจุด R | ทุกคอลัมน์ของ CSV กรองเฉพาะแถวที่ติด flag ได้ และดาวน์โหลด CSV |

แท็บ ink mask แสดงภาพที่โมเดลครอปเห็นจริงก่อนตีกรอบ เลือกวิธี binarization ได้ 6 แบบ
พร้อมปรับ `blackhat thr` / `hysteresis` / เชื่อมเส้นขาด / ทำเส้นหนา แล้วภาพเปลี่ยนทันที
โดยไม่ต้องรันตรวจจับใหม่ ใช้ดูว่าปลายยอด R ยังอยู่ครบไหมและกริดเหลือมากจนกลบเส้นหรือเปล่า
(ค่าที่ตั้งไว้ถูกส่งไปกับการตรวจจับด้วย)

แถบ chip ด้านบนสรุปสถานะ และจะขึ้นคำเตือนเองเมื่อ px/mm ให้ HR ที่เป็นไปไม่ได้
ครอปกว้างหรือแคบเกินไปเทียบกับ RR หรือยังไม่ได้ตั้งคลาส R

### นำเข้าข้อมูลจากโครงโฟลเดอร์ภายนอก

ชุดข้อมูลที่คนจัดเองมักมาเป็น `<ประเภท>/<รหัส ชื่อ>/crop/*.jpg` คำสั่ง `import-tree`
คัดลอกเฉพาะภาพในโฟลเดอร์ `crop` เข้าทะเบียน โดยใช้ชื่อโฟลเดอร์ชั้นบนสุดเป็น **ประเภท**
ของสัตว์ทุกตัวข้างใน (ตัดเลขลำดับหน้าชื่อทิ้ง `1. Normal` -> `Normal`)

```bash
docker compose run --rm -v "/path/ต้นทาง:/src:ro" web python -m ekg_rpeak.cli import-tree --src /src --data data --replace
```

`--replace` ลบภาพเดิมของรหัสที่ชนกันก่อนใส่ชุดใหม่ `--limit N` จำกัดจำนวนภาพต่อตัว
`--subdir` เปลี่ยนชื่อโฟลเดอร์ภาพที่จะเอา (ค่าเริ่มต้น `crop` เทียบแบบไม่สนตัวพิมพ์)

ตัวนำเข้ายอมรับความเพี้ยนที่เจอจริงในข้อมูลและแก้ให้เอง: โฟลเดอร์สะกด `crop`/`Crop`
สลับกัน, ไฟล์ภาพที่นามสกุลหลุด (ตัดสินจากไบต์แรกไม่ใช่ชื่อไฟล์), ชื่อไฟล์อ่านไม่รู้เรื่อง
จึงตั้งใหม่เป็น `<รหัส> <ชื่อ> <ลำดับ>.jpg`, และรหัสเดิมที่ต่างกันแค่ตัวพิมพ์
(`C56153` กับ `c56153` เป็นโฟลเดอร์เดียวกันบน Windows แต่เป็นคนละระเบียนในทะเบียน)

### รันทุกภาพไว้ล่วงหน้า

```bash
docker compose run --rm --no-deps web python -m ekg_rpeak.cli warm --images data --out out
```

รันทุกภาพใน `data/` แล้วเก็บผลลงดิสก์ หน้าเว็บอ่านผลชุดเดียวกันนี้ ผู้ใช้จึงเปิดดูสัตว์
ตัวไหนก็เห็นผลทันทีโดยไม่ต้องกดวิเคราะห์ สั่งซ้ำได้ ภาพที่มีผลตรงกับค่าตั้งปัจจุบันจะถูกข้าม
(`--force` เพื่อรันใหม่ทั้งหมด)

ผลถูกทิ้งเองเมื่อภาพต้นทางถูกแก้ (เทียบ mtime) ค่าตั้งไม่ตรงกับตอนที่รัน หรือรูปแบบที่เก็บ
เปลี่ยนรุ่น — กรณีแบบนั้นถือว่าไม่มีผล ให้รันใหม่ ดีกว่าแสดงตัวเลขที่ไม่ตรงกับภาพตรงหน้า

ภาพต้นฉบับไม่ถูกเก็บซ้ำลงดิสก์ (อ่านคืนจากไฟล์เดิม) และถูกถือไว้ในหน่วยความจำแค่ 12 ภาพ
ล่าสุด ชุดข้อมูลหลายสิบภาพจึงไม่ทำให้เซิร์ฟเวอร์บวม

## โครงสร้าง

| ไฟล์ | หน้าที่ |
|------|--------|
| `ekg_rpeak/config.py` | ค่าตั้งทั้งหมดใน `Config` เดียว แก้ผ่าน CLI หรือ `cfg.with_(...)` |
| `ekg_rpeak/preprocess.py` | Blackhat (โมเดลครอป), ink mask (โมเดลจุด), หายอด R (anchor) |
| `ekg_rpeak/geometry.py` | ครอปตามสัดส่วนชุดเทรน, map พิกัดกลับ, จัดแถว lead, เลือกจุด R, ตัดจุดซ้ำ |
| `ekg_rpeak/scale.py` | วัด px ต่อ mm จากกริดเล็กด้วย autocorrelation และตรวจความสมเหตุสมผล |
| `ekg_rpeak/grid.py` | หาเส้นกริดหลัก 5 mm ตั้งจุด x = 0 และสรุป RR เป็นมิลลิเมตร |
| `ekg_rpeak/render.py` | วาด overlay: กรอบจังหวะ, จุด R, landmark อื่น, เส้นกริดอ้างอิง |
| `ekg_rpeak/patients.py` | ทะเบียนสัตว์: โฟลเดอร์ตามรหัส, `patients.json`, เพิ่ม/ลบภาพ, จัดกลุ่มภาพเก่า |
| `ekg_rpeak/importer.py` | ดึงภาพจากโครงโฟลเดอร์ภายนอก `<ประเภท>/<รหัส ชื่อ>/<crop>` เข้าทะเบียน |
| `ekg_rpeak/results.py` | เก็บ/อ่านผลตรวจจับเป็น JSON ต่อภาพ ที่ `out/results/` |
| `ekg_rpeak/domain.py` | วัดว่าภาพที่จะป้อนโมเดล ใกล้ชุดที่โมเดลเห็นตอนเทรนแค่ไหน |
| `ekg_rpeak/rrstats.py` | สรุปช่วง RR ของสัตว์หนึ่งตัวด้วยสามวิธี พร้อมความคลาดเคลื่อน |
| `ekg_rpeak/pipeline.py` | ต่อทุกชั้นเข้าด้วยกัน คืน peaks + landmarks + stats |
| `ekg_rpeak/export.py` | CSV: RR-interval (px/mm/วินาที), bpm, flag คุณภาพ |
| `ekg_rpeak/cli.py` | คำสั่ง `info` / `scale` / `calibrate` / `detect` / `import-tree` / `warm` / `domain` |
| `webapp/server.py` | FastAPI: รันไปป์ไลน์ (จำผลไว้), ทะเบียนสัตว์, วาด overlay/ครอป/mask, ส่ง CSV |
| `webapp/static/` | หน้าเว็บ (HTML/CSS/JS ล้วน ไม่มี build step) |

## สิ่งที่ต้องตั้งก่อนใช้จริง

**1. weights** ไฟล์ `.pt` ไม่ได้อยู่ใน repo (ใหญ่เกินไป) ต้องวางเองที่ `models/`

| ไฟล์ | ที่มา |
|------|-------|
| `models/crop_best.pt` | โมเดลครอป กินภาพ Blackhat |
| `models/point_ink_best.pt` | โมเดลจุด **เทรนด้วยภาพ ink mask** จึงต้องใช้คู่กับ `point_pre='ink'` |

ถ้าไม่มีโมเดลจุด ไปป์ไลน์จะใช้ anchor จาก image processing อย่างเดียว ซึ่งยังได้ตำแหน่ง R ครบ

**2. คลาส R** โมเดลจุดเป็น multi-class landmark detector 11 คลาส
`{0:P1, 1:P2, 2:P3, 3:Q1, 4:Q2, 5:R, 6:S1, 7:S2, 8:T1, 9:T2, 10:T3}`
ค่าเริ่มต้นตั้ง `r_class_id = 5` ไว้แล้ว ถ้าเปลี่ยน weights ให้ตรวจด้วย `app info` ก่อน

**3. `train_px_per_mm`** วัดจากภาพชุดเทรนโมเดลจุดหนึ่งภาพ

```bash
docker compose run --rm app calibrate --image data/train_sample.png
```

### ค่าเริ่มต้นปัจจุบัน

| ค่า | ค่าเริ่มต้น | ทำไม |
|-----|------------|------|
| `point_weights` | `models/point_ink_best.pt` | เทรนบนภาพ ink mask |
| `point_pre` | `red_ink` | ตัดกริดด้วยแชนเนลแดงแทน saturation แล้วดึงคอนทราสต์ |
| `crop_mode` | `train_match` | ครอปด้วยสัดส่วนเดียวกับที่ dataset ตัดมา |
| `r_class_id` | `5` | ดัชนีคลาส R ของ weights ชุดนี้ |
| `point_conf` | `0.05` | โมเดลให้ conf ต่ำ (สูงสุด ~0.4) กรองสูงกว่านี้จะตัดจุดที่ถูกทิ้ง |
| `crop_conf` | `0.20` | 0.40 ทำให้จังหวะจริงหลุด วัดกับ 67 ภาพแล้วได้กล่องเพิ่ม 76 ใบ ไม่มีภาพไหนแย่ลง |
| `crop_pre` | `blackhat` | ต้องตรงกับที่ weights เห็นตอนเทรน |
| `anchor_expand_y` | `0.35` | ขยาย ROI แนวตั้งก่อนหายอด เพราะกล่องจากโมเดลครอปตัดยอดทิ้ง |

สามค่าแรกผูกกับ weights ที่โหลดอยู่ **ต้องเปลี่ยนพร้อมกัน** ถ้าสลับไปใช้ weights ที่เทรน
บนภาพเทา ต้องตั้ง `point_pre='gray'` ด้วย ไม่งั้นโมเดลจะเจอภาพคนละโดเมนกับตอนเทรน
และตรวจไม่พบอะไรเลย — เคยวัดได้ว่าเรื่องนี้ทำให้อัตราการเจอตกจาก 100% เหลือ 47%

สัดส่วนกรอบครอป `train_frame_w_ratio = 1.40`, `train_frame_h_ratio = 1.49` ตรงกับสคริปต์
ที่เทรนโมเดลจุด เทียบครอปของเรากับครอปชุดเทรนแล้วรูปทรงใกล้ที่สุด (ระยะห่างของโปรไฟล์หมึก
0.21 เทียบกับ 0.50 ของ 1.07/1.25) เห็น P กับ T ครบเฟรมเหมือนภาพชุดเทรน

ราคาที่จ่ายคือครอปของจังหวะข้างเคียงซ้อนกันมากขึ้น วัดกับ 67 ภาพแล้วจุดซ้ำเพิ่มจาก 15 เป็น 18
และโมเดลจุดยืนยันน้อยลง 10 จุดจาก 1380 แลกกับ flag ที่ลดจาก 83 เหลือ 80

## กล่องของโมเดลครอปตัดยอด R ทิ้ง

โมเดลครอปกินภาพ blackhat ที่ผ่าน threshold แล้ว ปลายยอด R ที่หมึกจาง (เทา ~150-200)
หลุดจาก binarization ไป ขอบบนของกล่องจึงอยู่ต่ำกว่ายอดจริงหลายสิบพิกเซล
วัดกับชุดข้อมูล 67 ภาพ: **11.6% ของกล่องตัดยอด เฉลี่ยขาดไป 19 px**

กล่องเป็นแค่ตัวระบุตำแหน่ง ค่าที่รายงานจริงมาจาก `find_r_anchor` ซึ่งเดิมจำกัด ROI
ไว้ที่ขอบกล่องพอดี anchor จึงไปติดขอบแทนที่จะเจอยอด `anchor_expand_y = 0.35`
แก้ตรงนี้ — วัดกับภาพจริงได้ความคลาดเคลื่อนของ y ลดจากมัธยฐาน 52 px เหลือ 2.6 px
และจำนวนจุดที่โมเดลจุดยืนยันเพิ่มจาก 6 เป็น 11 ในภาพเดียวกัน เพราะครอปที่ป้อนเข้าไป
ถูกจัดเฟรมด้วยแอมพลิจูดที่ถูกต้อง

| thr 15 แบ่ง 3 ท่อน | 1729 | 0.402 | 206 | 0.230 |

ได้กล่องเยอะขึ้นก็จริง แต่ระยะห่างระหว่างจังหวะกระจายขึ้นและกล่องซ้อนกันมากขึ้น
คือได้กล่องขยะ ไม่ใช่จังหวะที่หายไป **ค่าปัจจุบันจึงเป็นจุดที่ดีที่สุดสำหรับ weights ชุดนี้**

ความเหมือนของสถิติระดับพิกเซลไม่พอจะปิดช่องว่างนี้ ทางที่เหลือคือเทรนใหม่บนโดเมนปลายทาง

### ทำไมไม่แก้ที่ binarization

ลองแล้ว วัดกับ 67 ภาพครบทุกวิธี — **ไม่มีวิธีไหนแก้ปัญหานี้ได้** เพราะการตัดยอด
เป็นนิสัยของ label ที่ใช้เทรน ไม่ใช่ของ preprocessing

| `crop_pre` | กล่องรวม | กล่องที่ตัดยอด | หมายเหตุ |
|-----------|---------:|--------------:|---------|
| `blackhat` | 1439 | 11.6% | ตรงกับชุดเทรน กริดเหลือเป็นจุดดำเต็มภาพ (พิกเซลเส้น 15%) |
| `tophat_red` | — | — | **ค่าเริ่มต้นปัจจุบัน** — ทำ tophat บนแชนเนลแดง กริดหายมากสุด |
| `blackhat_otsu` | 1409 | — | เกณฑ์ปรับตามภาพ กริดน้อยลงครึ่งหนึ่ง |
| `tophat_gray` | 1463 | — | กล่องมากสุด แต่ตัดยอดลึกกว่า |
| `adaptive` | 1430 | — | ตัดยอดบ่อยที่สุด |
| `ink` | 752 | — | สะอาดที่สุดแต่หลุดโดเมน โมเดลอ่านไม่ออก เส้นขาดเป็นช่วง 5% |
| `red` + `crop_pre_hyst=0.5` | 1418 | **3.9%** | กริดหายหมด เส้นต่อเนื่อง 100% |

`red` ใช้แชนเนลแดงอย่างเดียว — กริดพิมพ์ด้วยหมึกแดงจึงสว่างเกือบเท่ากระดาษ
ส่วนเส้นคลื่นสีดำยังเข้ม ได้ภาพที่สะอาดกว่ามากโดยไม่ต้องพึ่ง saturation
`crop_pre_hyst` เติม hysteresis: ใช้เกณฑ์เข้มหาแกนเส้น แล้วต่อยอดด้วยเกณฑ์อ่อน
เฉพาะส่วนที่ติดกับแกน จึงเก็บปลายยอดที่จางไว้ได้โดยไม่ลากกริดเข้ามา

ไปป์ไลน์เต็มบน 67 ภาพให้ผลก้ำกึ่ง: `red+hyst` ได้ flag น้อยลง (83 -> 75) จุดที่โมเดล
ยืนยันมากขึ้นเล็กน้อย แต่ได้จุด R น้อยลง 2.5% **ค่าเริ่มต้นจึงยังเป็น `blackhat`**
ซึ่งตรงกับโดเมนที่ weights เห็นตอนเทรน ทางที่ควรได้ผลจริงคือเทรนโมเดลครอปใหม่
บนภาพแชนเนลแดง ไม่ใช่ป้อนภาพคนละโดเมนให้ weights ชุดเดิม

```bash
docker compose run --rm --no-deps web python -m ekg_rpeak.cli warm --images data --out out --force --crop-pre red --crop-pre-hyst 0.5
```

### ทำไมค่าเริ่มต้นเป็น tophat_red

เส้นกริดหลักทุก 5 mm รอด `tophat_gray` มาเป็น**แท่งทึบ** พาดทั้งแนวตั้งและแนวนอน
ยอด R ที่บังเอิญพาดทับเส้นกริดจึงกลืนหายไปกับแท่งนั้น โมเดลครอปมองไม่เห็นว่าเป็นจังหวะ
(เจอจริงที่ `661627 methung 1.jpg` กล่องที่ 11 กับ 13)

การทำ tophat บน**แชนเนลแดง**ลบกริดตั้งแต่ต้นทาง เพราะกริดพิมพ์ด้วยหมึกแดงจึงสว่าง
เกือบเท่ากระดาษในแชนเนลนั้น ผลคือ **ไม่ไวต่อ threshold** — เก็บจังหวะที่หายได้ครบ
ตั้งแต่ `crop_pre_thr` 18 ถึง 45 ขณะที่ `tophat_gray` ต้องดันถึง 35 ขึ้นไปจึงจะได้

### preprocessing ของโมเดลจุด

R อยู่ใกล้ขอบบนของครอปเสมอ วัดจาก 701 จังหวะในชุดนี้ได้ **y = 0.102 ของความสูงครอป**
(ตั้งไว้ 0.095) และ **99% อยู่ใน 30% บนสุด** ส่วน x = 0.459 (ตั้งไว้ 0.454) — ค่าที่ตั้งไว้แม่นแล้ว

เทียบวิธี preprocessing ที่ป้อนโมเดลจุด วัดกับทั้ง 67 ภาพ ตัวชี้วัดคือสัดส่วนจุดที่

| `point_pre` | จุด R | จากโมเดล | สัดส่วน | ต้องพึ่ง anchor |
|---|---:|---:|---:|---:|
| **`red_ink`** | 1407 | **1322** | **94.0%** | **101** |
| `ink` (ตรงกับชุดเทรน) | 1406 | 1253 | 89.1% | 170 |
| `red_contrast` | 1406 | 1091 | 77.6% | 332 |

`red_ink` สร้าง ink mask จากแชนเนลแดงแทนการดู saturation แล้วดึงคอนทราสต์ก่อน threshold
กริดที่เคยรอดมาปนจึงหายไป และปลายยอดที่หมึกจางไม่หลุด ผลคือโมเดลจุดยืนยันได้มากขึ้น 69 จุด

## การวัด px ต่อ mm

วัดจากคาบของเส้นกริดสองทาง เลือกอัตโนมัติด้วย `scale_source`

| ค่า | ทำอย่างไร |
|---|---|
| `minor` | วัดคาบกริดเล็ก 1 mm ด้วย autocorrelation |
| `major` | ถือว่า **หนึ่งช่องกริดหลัก = `grid_mm` (5) มิลลิเมตร** แล้วหารด้วย 5 |
| `auto` (ค่าเริ่มต้น) | ใช้ `minor` ก่อน ถ้าให้อัตราการเต้นที่เป็นไปไม่ได้จึงเปลี่ยนไปใช้ `major` |

โปรไฟล์กริดมียอด autocorrelation ทั้งที่คาบมูลฐานและที่พหุคูณของมัน การเลือกเองว่าอันไหน
คือช่องหลักจึงผิดเป็นจำนวนเท่าได้ ตัวตัดสินคือ **ช่วงอัตราการเต้นที่เป็นไปได้**
(`scale_hr_lo` ถึง `scale_hr_hi` = 40–300 bpm) คำนวณจากระยะระหว่างจังหวะที่วัดได้แล้ว

นี่คือการใช้ความรู้ล่วงหน้าทางสรีรวิทยา **ไม่ใช่การวัด** ระบบจึงรายงานที่มาของค่าไว้เสมอ —
หน้าเว็บขึ้น chip "ที่มาของ px/mm" และคำอธิบายใต้แถบสถานะเมื่อค่ามาจากช่องกริดหลัก

ผลกับชุดข้อมูล 67 ภาพ: ภาพที่ให้อัตราการเต้นเป็นไปได้เพิ่มจาก **39 เป็น 67 ภาพ**
โดย 28 ภาพเปลี่ยนไปใช้ `major` ทำให้สุนัขที่มีข้อมูล RR ใช้ได้เพิ่มจาก 21 เป็น **31 ตัวครบ**

## หน้าสรุป RR รายตัว

`/rr.html` — รวมค่า RR จากทุกภาพของสัตว์ตัวเดียวกัน แล้วสรุปด้วยสามวิธีเพื่อให้เทียบกันได้

| วิธี | คำนวณอย่างไร | ลักษณะ |
|---|---|---|
| `mean_all` | เฉลี่ยค่า RR ทุกช่วง | ใช้ข้อมูลครบ ถูกช่วงที่ยาวผิดปกติลากง่ายที่สุด |
| `mid20` | เรียงแล้วเอา 20 ค่าตรงกลางมาเฉลี่ย | ตัดหางสองข้าง ทนค่าผิดปกติโดยยังใช้ข้อมูลเชิงปริมาณ |
| `median` | มัธยฐานของทุกช่วง | ทนค่าผิดปกติที่สุด ความไม่แน่นอนของค่ากลางกว้างกว่า |

แต่ละวิธีรายงานค่า จำนวนที่ใช้ SD และ SEM พร้อมค่า min/max/SD ของ RR ทั้งหมด และ
**ต่างสุด** คือความไม่ลงรอยระหว่างสามวิธี ซึ่งใช้เป็นสัญญาณว่าตัวนั้นมีค่าผิดปกติปนอยู่

`mid20` ตัดข้างล่างมากกว่าหนึ่งค่าเมื่อจำนวนที่ต้องตัดเป็นเลขคี่ เพราะช่วงที่ยาวผิดปกติ
มาจากจังหวะที่หายไป ซึ่งอันตรายกว่าช่วงที่สั้นผิดปกติ

**ภาพที่วัด px/mm ผิดถูกตัดออกโดยค่าเริ่มต้น** (ดูหัวข้อถัดไป) เพราะ RR ของภาพนั้นผิดตามไปทั้งภาพ
ปิดการตัดออกได้จากช่องกาในหน้าเว็บ ตารางส่งออกเป็น CSV ได้ที่ `/api/rr-summary.csv`

## หน้าเทียบสองชุด (debug)

`/debug.html` — อัปโหลดภาพชุดเทรนกับชุดที่จะเอาไปใช้จริง **ตั้งค่าประมวลผลแยกกันได้**
เพราะเป็นข้อมูลคนละที่มา ไม่มีเหตุผลให้บังคับใช้ค่าเดียวกัน สิ่งที่ต้องเทียบคือผลลัพธ์ปลายทาง

แต่ละฝั่งรันไปป์ไลน์เต็มแล้วแสดงตารางรายภาพ (จังหวะ / จุด R / จากโมเดล / anchor / จุดซ้ำ /
flag / px per mm / RR / HR) พร้อม overlay และครอปที่ป้อนโมเดลจุด แถบบนสุดเทียบสองฝั่ง
และทำเป็นสีแดงเมื่อ **สัดส่วนที่โมเดลยืนยันต่างกันเกิน 15%** หรือ **flag ต่อจุดต่างกันเกิน 5%**
ซึ่งเป็นสัญญาณว่าชุดหนึ่งหลุดโดเมนไปจากอีกชุด

แต่ละฝั่งใส่ภาพได้สองทาง: อัปโหลดไฟล์ใหม่ หรือ**เลือกจากภาพที่มีอยู่แล้วใน `data/`**
(กรองด้วยชื่อ รหัส หรือประเภทได้ เลือกทั้งหมดที่กรองอยู่ได้ในคลิกเดียว) ภาพที่เลือกจาก
`data/` ถูกอ้างถึงเฉย ๆ ไม่คัดลอก เพราะเป็นข้อมูลผู้ป่วย ไม่ควรมีสำเนาเพิ่ม
เปลี่ยนรายการที่เลือกแล้วผลเดิมของฝั่งนั้นถูกทิ้งทันที ป้องกันการเทียบกับผลค้าง

ภาพที่อัปโหลดไปอยู่ที่ `out/debug/<train|test>/` แยกจาก `data/` จึงไม่ปนกับทะเบียนสัตว์

## หลักการที่โค้ดยึด

- **โมเดลแต่ละตัวต้องได้อินพุตในโดเมนเดียวกับตอนเทรน** โมเดลครอปกินภาพ Blackhat
  โมเดลจุดกินครอปที่ลบพื้นหลังกริดด้วย ink mask ตัวเดียวกับที่ใช้ตอนเทรน
  และทั้งคู่เทรนที่ `imgsz=512` (จาก `args.yaml`)
- **สเกลอ้างอิงเส้นกริด ไม่ใช่ขนาดกล่อง** ขนาดครอปคิดเป็นมิลลิเมตรจริง จึงไม่แปรตาม DPI ของสแกนเนอร์
- **ระยะทุกค่าวัดจากเส้นกริดหลัก 5 mm ของภาพเอง** ไม่ต้องรู้ DPI ล่วงหน้า `x = 0` คือเส้นกริด
  ที่อยู่นอกจังหวะซ้ายสุด ทำให้ตัวเลขในรายงานอ้างอิงกับสิ่งที่มองเห็นบนกระดาษได้ตรง ๆ
- **แยกเส้นคลื่นจากกริดด้วยสี ไม่ใช่ความเข้ม** เส้นกริดหลักทุก 5 mm เข้มพอ ๆ กับเส้นคลื่น แต่มีสีเสมอ
- **โมเดลจุดเป็นตัวขัดเกลา ไม่ใช่ตัวตัดสินคนเดียว** ถ้ามันเงียบหรือชี้ไกลจาก anchor ด้วย conf ต่ำ
  ระบบใช้ anchor แทน และนับไว้ใน stats ให้ตรวจสอบได้
- **ความผิดพลาดต้องมองเห็น** คอลัมน์ `flag` เตือน `missed_beat?` / `duplicate?`
  และ `src` บอกว่าจุดนั้นมาจากโมเดลหรือ anchor
- **รหัสรุ่นของผลคิดจากเนื้อหา ไม่ใช่ลำดับ** ภาพ overlay ถูกส่งแบบ `immutable` อายุหนึ่งปี
  URL จึงต้องมีรหัสที่เปลี่ยนเมื่อผลเปลี่ยนเท่านั้น ถ้าใช้ตัวนับ เลขจะเริ่มใหม่ทุกครั้งที่
  รีสตาร์ต ภาพคนละใบได้เลขซ้ำกัน แล้วเบราว์เซอร์จะแสดงภาพเก่าคู่กับตัวเลขชุดใหม่
  โดยไม่มีอะไรบอก — `results.revision()` จึงคิดจาก (ชื่อภาพ + เวลาแก้ไข + ค่าตั้ง)
